## 0. 一句话作用

讲清 Apollo 全链路消息的**四件公共基建**：时间源（`cyber::Time` / `cyber::Clock`）、消息头（`apollo.common.Header` + `FillHeader`）、收发通道（`Node::CreateWriter/CreateReader` → `Writer::Write` / `Reader::Observe`）、以及 channel 名与 C++ 消息类型的**绑定关系**（dag readers 下标 ↔ 组件模板参数 M0..M3）。所有 PnC 模块（planning/control/canbus/…）的时间戳与收发写法都落在这一层，模块篇只写差异。

## 2. 机制与数据流

### 2.1 时间机制：三层时间源，单位各不同

| 用途 | 该用什么 | 单位 | 证据 |
|---|---|---|---|
| **消息 header 时间戳** | `apollo::cyber::Clock::NowInSeconds()` | double **秒** | message_util.h:47-49 即如此 |
| 仿真/回放时间可控 | `Clock::Now()`（MOCK 模式返回 `SetNow` 灌入的时间） | — | clock.cc:40-54、82-90 |
| 代码段耗时测量 | `Time::MonoTime()`（steady）或 `Clock::Now()` 差值 → `Duration::ToSecond()` | 秒/毫秒自算 | time.cc:67-75；control_component.cc:518-520（`(end-start).ToSecond()*1e3` 得毫秒） |
| 框架内部延迟采样 | `Time::Now().ToMicrosecond()` | **微秒** | component.h:193、200、428、435 |
| 传感器时间 | header 的 `lidar/camera/radar_timestamp` | **纳秒 uint64** | header.proto:18-25 |

即：**秒（header）/ 毫秒（日志与周期）/ 微秒（框架延迟统计）/ 纳秒（Time 内部与传感器戳）四种单位并存**，跨层引用必须显式换算。

### 2.3 `FillHeader` 与真实写头样例（都在本轮 read 核过）

`message_util.h:44-52` 全文语义：

- `static std::atomic<uint64_t> sequence_num = {0}`（:45）——**模板函数内的 static，每个消息类型 T 各有一份计数器**，不是全进程统一序号；
- `set_module_name(module_name)`（:48）、`set_timestamp_sec(Clock::NowInSeconds())`（:47、49）、`set_sequence_num(sequence_num.fetch_add(1))`（:50-51）；
- **只填这 3 个字段**，`lidar/camera/radar_timestamp`、`status`、`frame_id` 一律不填。

样例 ①（planning 输出，planning_component.cc:225-236）：`RunOnce` 先在 header 里留了规划起点时间 → `:227` 取出作 `start_time` → `:228 FillHeader(node_->Name(), &adc_trajectory_pb)` **覆盖** `timestamp_sec` → `:232-235` 用 `dt = start_time - 新 header 时间` 逐点修正 `relative_time` → `:236 planning_writer_->Write(...)`。同文件 `:216-217` 是 learning data 的同样写法。

样例 ②（control 输出，control_component.cc:490-508）：`:490` 存 status → `:493-499` 用 `local_view_.trajectory().header().lidar_timestamp()` 做端到端延迟记录（`LatencyRecorder`）→ `:501 FillHeader(node_->Name(), &control_command)` → `:502-505` `FLAGS_sim_by_record` 时把 `timestamp_sec` 改成 chassis 的 header 时间 → `:508 control_cmd_writer_->Write(control_command)`。

样例 ③（传感器戳透传，planning_base.cc:98-107 `FillPlanningPb`）：`:100` 写入传入的 timestamp，`:101-107` 若 prediction 有 header，则把 `lidar/camera/radar_timestamp` 原样拷进 ADCTrajectory —— 这条链是 control 侧延迟统计能工作的前提。

### 2.5 消息类型绑定：channel 名是运行期字符串，类型来自模板参数

`NodeChannelImpl::FillInAttr<MessageT>`（node_channel_impl.h:234-255）在每次建 writer/reader 时填 `RoleAttributes`：`set_channel_id(GlobalData::RegisterChannel(channel_name))`（241-242）、`set_message_type(message::MessageType<MessageT>())`（243-245）、`proto_desc`（246-250）、缺省 QoS（251-254）。空 channel 名 → `AERROR` + nullptr（154-157 写侧、206-209 读侧）；非 reality 模式换成进程内 `IntraWriter/IntraReader`（162-166、215-221）。

组件层的 dag ↔ 模板参数对应（component.h，**下标严格对应**）：

| 模板形态 | readers 数量校验 | 绑定关系 | 行号(已核) |
|---|---|---|---|
| `Component<M0>` | `readers_size() < 1` → AERROR + false | M0 ← `readers(0)` | 169-172；181-184 |
| `Component<M0,M1>` | `< 2` → false | M1 ← `readers(1)`；M0 ← `readers(0)` | 255-258；267-272；274-284 |
| `Component<M0,M1,M2>` | `< 3` → false | M1←`readers(1)`、M2←`readers(2)`、M0←`readers(0)` | 380-383；393-403；405-415 |

M0 永远是**触发源**：reality 模式下只给 M0 建协程任务/DataVisitor（单消息版 231-237），非 reality 模式下 M1/M2 走 blocker 取最新值、且两者都非空才 `Process`（421-434）。M3 形态（4 消息）同文件更后段，本轮未 read 到，规律待核。

### 2.6 类型不匹配的后果（有代码证据）

`ChannelManager::ScanMessageType`（channel_manager.cc:314-348）：每有新 reader/writer 加入拓扑，就与该 channel 上已存在的 writer（321-333）与 reader（335-347）逐个比 `IsMessageTypeMatching`，不一致时打 **AERROR**「newly added reader/writer ... 's message type[X] does not match the exsited writer/reader ...'s message type[Y]」（326-331、340-345）。判定本身很宽：字符串全等，或任一方在 `exempted_msg_types_` 内即算匹配（211-223，即 RawMessage 这类通用类型豁免）。

**结论：类型写错不会阻止建链、不会让进程退出，只在日志里留一条 AERROR**；下游拿到的是按错类型反序列化的结果（收不到 / 字段乱）。同理 dag 里 channel 名拼错也完全静默：reader 建成功，只是永远没数据。排查唯一入口是日志 + `cyber_channel`（§6）。

## 3. 注册与配置

- **时间源配置**：Clock 的初始模式来自 cyber 自身 conf 的 `run_mode_conf.clock_mode`（clock.cc:33-38，proto 在 `/opt/apollo/neo/src/cyber/proto/run_mode_conf.proto`，本轮未 read）；业务侧另有 `--use_sim_time`（定义在 `/opt/apollo/neo/src/modules/common/configs/config_gflags.cc`，grep 定位、行号待核）与 `/apollo/modules/common/data/global_flagfile.txt` 内的同名开关（引自 `.manual_work/inventory/cyber_messages_inventory.md` §6.2，本轮未重开）。
- **topic 配置**：新增/改默认 topic 名要同时改 `adapter_gflags.cc` 与 `adapter_gflags.h`（gflags 铁律，CLAUDE.md §4）；planning 这类把 topic 收进 conf proto 的模块，还要保证 dag readers 与 conf 里的对应字段一致（两处，改一处即错位）。
- **收发无需注册**：Writer/Reader 不进 plugins.xml，`CreateWriter/CreateReader` 是纯运行期行为；只有组件本身要 `CYBER_REGISTER_COMPONENT`（component.h:657-658，引自 inventory，本篇未重核）。
- **QoS/队列深度**：dag 的 `qos_profile{depth:N}` 与 `pending_queue_size:N` 直接进 `ReaderConfig`（component.h:181-184、267-270、393-401），代码里建 reader 则由 `Reader` 构造第三参决定（reader.h:87-89）。

## 4. 修改与扩展点（二次开发）

1. **加一路输出 channel**：组件 `Init()` 里 `xxx_writer_ = node_->CreateWriter<Msg>(<topic>)`（样板 timer_component_example.cc:24；生产样板 planning_component.cc:236 的 writer 用法），`Proc()` 里先 `common::util::FillHeader(node_->Name(), &msg)` 再 `xxx_writer_->Write(msg)`。topic 值优先放进本模块 conf proto，其次加 `adapter_gflags.cc/.h` 的 `DEFINE_string`；改完 `buildtool build -p modules/<你的包路径>`（只 `bazel build` 不 install，运行时看不见）。
2. **加一路输入 channel**：若是触发源之外的侧输入 → `Init()` 里 `node_->CreateReader<Msg>(topic, [this](const std::shared_ptr<Msg>& m){ std::lock_guard<std::mutex> lk(mtx_); cache_ = *m; })`（planning 侧信道即此形，见 12 篇 §2.3）。若要作为触发条件 → 改组件模板参数 `Component<M0,M1,...>` **并在 dag readers 里按同一下标顺序追加**（§2.5），漏加 → `Initialize` 直接 false，模块起不来。
3. **打时间戳**：一律走 `apollo::cyber::Clock::NowInSeconds()`（clock.h:60），**不要**直接 `std::chrono` 或 `Time::Now()`——否则 MOCK/回放模式下时间不跟 bag 走。测耗时用 `Time::MonoTime()` 或 `Clock::Now()` 差值 `.ToSecond()*1e3`（control_component.cc:518-520 样板）。
4. **端到端延迟追踪**：把上游 header 的 `lidar_timestamp` 透传下去（planning_base.cc:101-107 样板），下游用 `LatencyRecorder`（control_component.cc:493-499 样板）。
5. **改队列深度防丢帧**：dag 里给对应 reader 加 `pending_queue_size` 与 `qos_profile{depth}`（默认 1，reader.h:50）；改的是 ④ 层软链文件，`ls -l` / `readlink` 先认落点（profile 层或 share 层）。

## 5. ⚠️ 本环境注意

- **`sequence_num` 从 0 开始**：`fetch_add(1)` 返回旧值（message_util.h:50-51），首条消息 `sequence_num=0`，与 header.proto:14-15 注释「always starting from 1 on boot」**不一致**。别用 `sequence_num==1` 判首帧。
- **`sequence_num` 是「每消息类型一份」**：`static` 位于模板函数内（message_util.h:44-45），同一进程不同消息类型各自独立计数，不是模块级全局序号。
- **`FillHeader` 会覆盖 `timestamp_sec`**：模块内部先写的 header 时间会被 component 层的 `FillHeader` 抹掉，planning 正是为此在 `:227-235` 用 `dt` 修正轨迹点 `relative_time`。自己新增输出时若依赖内部时间，要么先取出再修正，要么不调 `FillHeader`。
- **单位混用是延迟统计出错头号原因**：`timestamp_sec` 是 double 秒，`lidar/camera/radar_timestamp` 是 uint64 纳秒（header.proto:9、18-25），框架延迟采样又是微秒（component.h:193、200）。
- **`Time::Now()` 是墙钟**（`high_resolution_clock`，time.cc:57-65），会被系统对时跳变影响；单调时间要 `MonoTime()`（:67-75）。
- **MOCK 时钟没人 `SetNow` 就恒为 0**：`Clock` 构造把 `mock_now_ = Time(0)`（clock.cc:37），`SetMode` 也会把它清零（cc:73）；MOCK 模式下若无人灌时间，所有 header `timestamp_sec` 都是 0 —— 回放/仿真调试遇到「时间戳为 0」先查时钟模式，别先怀疑驱动。
- **消息类型不匹配不阻断**（channel_manager.cc:314-348）：只有一条 AERROR「does not match the exsited ...」；channel 名拼错则连日志都没有。dag 是运行期字符串，编译期不校验 —— 这是「模块起来了但收不到」的两大静默来源。
- **同 Node 重复订阅同一 channel 返回 nullptr**（node.h:207-212 等），不判空就用即段错误。
- **`pending_queue_size` 默认 1**（reader.h:50、62-66），处理慢即丢旧帧；planning 给 chassis/localization 显式设了 50（见 12 篇 §2.2）。
- **搜 `/apollo/...` 用 `grep -R`**（④ 层全是符号链接，`-r` 不跟随会假空，CLAUDE.md §3②）；改 conf/dag 前 `readlink` 认落点（profile 覆盖层 or share 出厂件）。
- **改完必须 `buildtool build -p <包路径>`** 才 install 到 `/opt/apollo/neo/{lib,share}`；运行时不读 `bazel-bin`（CLAUDE.md §2）。
