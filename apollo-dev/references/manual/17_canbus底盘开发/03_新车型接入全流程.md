## 0. 一句话作用

本文给"拿到一辆符合线控标准的车"到"Apollo 11.0 能控住它"的完整落地步骤：DBC 检查 → 官方工具 `gen_vehicle_protocol` 生成车型插件骨架 → 填控制/反馈逻辑 → 编译安装 → 改 canbus conf 选中新车 → 开环验证。**11.0 与官方 43 篇（9.0 口径）最大的不同是：生成的骨架是独立 `canbus_vehicle/<车型>` 插件包（含 vehicle_factory + cyberfile.xml），且选车靠 conf 的 `--load_vehicle_library/--load_vehicle_class_name`，不再改 `vehicle_factory.cc` 的 switch。**

## 2. 机制：DBC → 代码模板是怎么生成的

`gen.py` 流程（:61–81）：读 conf.yml → `extract_dbc_meta` 解析 DBC 成中间 yml → `gen_proto_file` 生成 `<car>.proto` → `gen_protocols` 生成 `protocol/` 每个报文的类（控制类 `UpdateData`、反馈类 `Parse`）→ `gen_vehicle_controller_and_manager` 生成 controller + message_manager（+ **vehicle_factory，见 template 里的 vehicle_factory.cc/.h.tpl**）→ `gen_canbus_conf` 生成 canbus 配置（`canbus_aem.conf.tpl`/`canbus_source.conf.tpl`/`canbus_conf.pb.tpl`）。**11.0 的模板集已按插件包形态升级**：生成物自带 `cyberfile.xml`（包的身份证）与 `vehicle_factory`，直接就是 `canbus_vehicle/<车型>` 的可编译包。`template_dir` 硬编码 `/apollo/modules/tools/gen_vehicle_protocol/template/`（gen.py:54）——本机该路径存在（bash 实测 `/apollo/modules/tools/gen_vehicle_protocol/template/` 可列）。

## 4. 注册与配置（选车即"注册"）

- 11.0 的"注册新车" = ① 插件 .so 装进 `/opt/apollo/neo/lib/modules/canbus_vehicle/<车>/`（`buildtool build -p` 完成 install）② conf 的 `--load_vehicle_library=<该 .so 绝对路径>` + `--load_vehicle_class_name=<类名>`。没有 plugins.xml、没有 brand switch、没有 class 枚举。
- `canbus_conf.pb.txt` 的 `vehicle_parameter.brand`（vehicle_parameter.proto:9）与 `can_card_parameter`（本机 HERMES_CAN/PCI_CARD/CHANNEL_ID_THREE）分别管"出厂车辆参数"与"CAN 卡型号"；`CanClientFactory` 按 `can_card_parameter.brand` 建对应 CAN 客户端（neolix factory.cc:34–36）。
- 配置改动落在 profile 覆盖层（`readlink` 见 01 篇 §3），立即生效，但**换到别的 profile/工作区要重核**。

## 5. ⚠️ 本环境注意（差异 + 坑）

- **官方 43 篇工具路径是 9.0 口径，11.0 有差异，待核**：43 篇写"把 DBC 放 `apollo/modules/tools/gen_vehicle_protocol`、`python gen.py`、产物拷进 `modules/canbus/vehicle/`"[官方·上游]——本机工具存在但**输出/合入路径已改为 `canbus_vehicle/<车型>` 插件包**（gen.py:53 打印 "Generate the canbus_vehicle output dir"）。模板集与 9.0 不同（多了 vehicle_factory/cyberfile.xml/canbus_*conf 模板，bash ls 实测）。**gen.py 的实际产出目录布局（output_dir/<car>/{proto,protocol,vehicle_factory…}）建议先跑一次 `use_demo_dbc` 样例核对再合入**（待核项）。
- **canbus 运行时必须真实底盘反馈**：开环/联调的前提是 CAN 卡与底盘通信（chassis_detail 非空）；没有底盘时 chassis 字段是 NaN/空，control 收到的是坏数据。纯软件验证只能靠 record 回放或 SimControl，不是 canbus 模块的职责。
- **标定表**：油门/刹车的标定（`control_conf` 里的 calibration_table，`buildtool install control` 后查 `modules/control/conf/` 与车型 profile）不在 canbus 里做；canbus 只管"百分比→CAN 报文"，"百分比↔加速度"的映射见 ../13_control源码/04_conf标定与调参.md。**新车型没标定表时控制层会用默认/空标定，车会不动或过冲，是"车不响应"的常见原因。**
- **44 篇 teleop 的 11.0 运行方式待核**：`/apollo/scripts/canbus_teleop.sh` 是软链到 `/opt/apollo/neo/share/scripts/canbus_teleop.sh`，内容 `./bazel-bin/modules/canbus/tools/teleop`（bash cat）——**整仓形态残留**，本机 `bazel-bin/` 不落运行产物（CLAUDE.md 第二节），且 canbus 不在工作区（`/apollo_workspace/modules/canbus/` 无 tools）。先用 `buildtool install canbus` 拉源码，再 `buildtool build -p modules/canbus` 后从工作区 `bazel-bin/` 跑 `teleop`，或直接 `bazel run //modules/canbus/tools:teleop`（待核是否满足）。
- **44 篇"改 conf 打开 chassis_detail/关 guardian"本机已默认**：当前 profile `canbus.conf` 已 `--enable_chassis_detail_pub` + `--noreceive_guardian`（01 篇 §3），联调前确认即可。
- **工具脚本坏参数提醒**：`cyber_channel -w` 在本环境是坏的（CLAUDE.md），看频率用 `cyber_monitor` 或 `cyber_channel -e`。
- 43 篇提醒"output 文件夹不删会编译报错"[官方·上游]——生成后及时拷走并清理 output。

## 6. 验证命令（实测过的）

```bash
# 工具可运行性（PyYAML 已装、模板目录在）
python3 -c "import yaml; print('yaml OK')"
ls /apollo/modules/tools/gen_vehicle_protocol/template/ | head

# 生成（在 src 只读层建议先 copy 一份 conf 到工作区再跑）
cd /opt/apollo/neo/src/modules/tools/gen_vehicle_protocol && python3 gen.py gem_conf.yml

# 编译安装插件（改完必做）
buildtool install canbus_vehicle           # 需要时可先拉包源码
buildtool build -p modules/canbus_vehicle/<车>

# 确认产物 + 选车配置
ls /opt/apollo/neo/lib/modules/canbus_vehicle/<车>/
grep -n "load_vehicle" /apollo/modules/canbus/conf/canbus.conf

# 启动 + 看底盘
mainboard -d /apollo/modules/canbus/dag/canbus.dag
cyber_channel -e /apollo/canbus/chassis
cyber_monitor
```
