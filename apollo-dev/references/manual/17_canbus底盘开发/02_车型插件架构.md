## 0. 一句话作用

11.0 把每种车型做成一个**独立 canbus_vehicle 插件包**（源码 `modules/canbus_vehicle/<车型>/`），内部四件套：`*_vehicle_factory`（工厂/注册入口）→ `*_controller`（整车控制：转向/油门/刹车/档位）→ `*_message_manager`（报文收发注册）→ `protocol/`（每个 CAN 报文的类）。canbus 主模块通过 ClassLoader 按 conf 指定的库路径+类名动态加载工厂（见 01 篇 §2.2），Chassis 就是在这条链路上被填出来的。

## 2. 机制与数据流

**2.1 插件如何被创建**：`canbus_component.cc:58–60` 用 `ClassLoader(FLAGS_load_vehicle_library)` + `CreateClassObj<AbstractVehicleFactory>(FLAGS_load_vehicle_class_name)` 实例化工厂（dlopen 该 .so，读静态注册表）。注册靠 `CYBER_REGISTER_VEHICLEFACTORY(类名)` → `CLASS_LOADER_REGISTER_CLASS(类名, AbstractVehicleFactory)`（abstract_vehicle_factory.h:135–136）。

**2.2 工厂 Init**（neolix_edu_vehicle_factory.cc:32–91）：
1. `CanClientFactory::Instance()->RegisterCanClients()` + `CreateCANClient(canbus_conf->can_card_parameter())` 建 CAN 卡客户端（:34–36，本机 HERMES_CAN）；
2. `CreateMessageManager()`（:43）→ `can_receiver_.Init(...)`（:50）→ `can_sender_.Init(...)`（:57）→ `CreateVehicleController()`（:64）→ `vehicle_controller_->Init(vehicle_parameter, &can_sender_, message_manager_)`（:71）；
3. `cyber::CreateNode("chassis_detail")`（:81）+ 建 `chassis_detail_writer_` / `chassis_detail_sender_writer_`（:83–88，topic 见 01 篇 §2 表）。

**2.3 工厂 Start**（:93–121）：先 `can_client_->Start()`（硬件上电）→ `can_receiver_.Start()` → `can_sender_.Start()` → `vehicle_controller_->Start()`（含 neolix 的 `SecurityDogThreadFunc` 安全监控线程）。

**2.4 Chassis 填充链路（下行+上行）**：
- **下行**：`/apollo/control` → `OnControlCommand` → `vehicle_object_->UpdateCommand`（neolix factory.cc:131–139）→ `vehicle_controller_->Update(*cmd)`（vehicle_controller.h:405–492：按 `driving_mode` 分派 `Gear/Throttle/Acceleration/Brake/Steer/SetEpbBreak`，把命令写进各控制协议类）→ `can_sender_.Update()` 组帧发 CAN。
- **上行**：`CanReceiver` 收帧 → 各 `ProtocolData::Parse` 把信号写进 `ChassisDetail`（`MessageManager::ParseCanMsg` 按报文 ID 分发给已注册的协议类）→ `controller->chassis()` 从 chassis_detail 里取字段拼 `Chassis`（如 43 篇 ge3 那段逐字段 `set_speed_mps/set_steering_percentage/...`，[官方·上游]）→ `factory->publish_chassis()`（neolix factory.cc:151–155）→ canbus `PublishChassis()` → `/apollo/canbus/chassis`。**`chassis_detail` 是每帧报文的原始回读**（同一 `Neolix_edu` proto），由 `PublishChassisDetail()`（:157–161）单独发 `/apollo/canbus/chassis_detail`。

**2.5 控制器接口要点**（vehicle_controller.h）：`Update` 公共实现按模式分派（:462–481：`COMPLETE_AUTO_DRIVE`/`AUTO_SPEED_ONLY` 走纵纵向+档位+EPB，`COMPLETE_AUTO_DRIVE`/`AUTO_STEER_ONLY` 走转向）；`SetDrivingMode` 状态机（:349–403，EMERGENCY_MODE 只能回 MANUAL）；`pad_msg` 的 START/RESET/VIN_REQ 处理（:413–460，VIN_REQ 调 `VerifyID()`）。派生类必须实现 `EnableAutoMode/DisableAutoMode/EnableSteeringOnlyMode/EnableSpeedOnlyMode/Emergency/Gear/Brake/Throttle/Acceleration/Steer×2/SetEpbBreak/SetBeam/SetHorn/SetTurningSignal/HandleCustomOperation/VerifyID`（:123–205）。

## 3. 注册与配置

- **注册机制 = cyber ClassLoader**：全仓 canbus_vehicle 下**没有 plugins.xml**（bash find 实测空），`/opt/apollo/neo/share/cyber_plugin_index/` 无 canbus_vehicle 条目。**结论：车型插件不是 PluginManager 插件，是 ClassLoader 类库**；"插件加载不到"排查方向是 .so 路径/类名（conf gflags）与 BUILD 的 `apollo_component` 产物名，不是 plugins.xml。
- **BUILD 产物命名**：neolix_edu/BUILD 里 `apollo_cc_library(name="apollo_canbus_vehicle_neolix_edu", srcs=[controller/message_manager/factory + protocol/*.cc], ...)` + `apollo_component(name="libneolix_edu_vehicle_factory_lib.so", deps=[...])`（bash 核对）——**.so 名必须与 conf 的 `--load_vehicle_library` 路径末段一致**。
- **11 款车型插件清单**（`/opt/apollo/neo/src/modules/canbus_vehicle/` 与 `/opt/apollo/neo/lib/modules/canbus_vehicle/` 一致，bash ls）：

| 车型 | 备注 |
|---|---|
| beiqi_arcfox | 本机 ARCF_40P profile 当前加载款 |
| ch / devkit / gem / transit / wey / zhongyun | 商用车/小车款 |
| ge3 | 43 篇示例款（[官方·上游]）|
| lexus / lincoln | 乘用车；lincoln 即 44/45 篇 MKZ（[官方·上游]）|
| neolix_edu | 本手册样板款（教育车）|

- **canbus 主模块 BUILD 不依赖任何车型库**：canbus/BUILD 有 `DO_NOT_IMPORT_canbus_component`（bash 核对）——车型靠运行时 ClassLoader 注入，这也是"换车只改 conf"的前提。

## 4. 修改与扩展点（二次开发）

| 想做什么 | 改哪里 |
|---|---|
| 改某车型的转向/油门/刹车逻辑 | `<车型>_controller.cc` 的 `Steer/Throttle/Brake/Gear/Enable*Mode` |
| 改/加一条 CAN 报文 | `protocol/<报文>.h/.cc`（控制类实现 `UpdateData`/`set_xxx`，反馈类实现 `Parse`）+ `message_manager.cc` 里注册 + BUILD srcs |
| 修改驾驶模式反馈映射（check_response） | 在反馈报文 `Parse` 里写 `chassis_detail.mutable_check_response()->set_is_eps_online(...)` 等（43 篇 :2496–2516 的做法，[官方·上游]）|
| 新增车型 | 见 03 篇全流程（推荐用 gen_vehicle_protocol 生成骨架）|
| 加自定义底盘状态 | 用 `Chassis.custom_status`（Any 字段，见 ../14_数据与消息/02_chassis与车辆参数.md §4）|

## 5. ⚠️ 本环境注意

- **注册宏在 .h 不在 .cc**（neolix_edu_vehicle_factory.h:164、lincoln_vehicle_factory.h:122）——头文件被 include 即注册，别在 .cc 里找宏。
- **插件的"注册"与 PluginManager 无关**：这是最容易搞混的点（planning/control 用 plugins.xml，车型用 class_loader），排查手段完全不同。
- **`vehicle_parameter.brand` 字段还在（vehicle_parameter.proto:9）但 11.0 不再用于选车型**——9.0 的 vehicle_factory.cc 按 brand switch 已删除（[官方·上游]43 篇该步骤在 11.0 不适用）。
- **车型 proto 是每款独立的**（`neolix_edu.proto`、`ge3.proto`…），`chassis_detail.proto` 里 `ChassisDetail` 不再 import 车型（9.0 是 `Ge3 ge3 = 21` 加进 ChassisDetail，[官方·上游]43 篇；11.0 各车型自己发自己的 detail 消息到 `/apollo/canbus/chassis_detail`）。
- **`SecurityDogThreadFunc`**（neolix_edu_controller.h:121）是 11.0 新增的底盘安全监控线程，新车型可借鉴：周期内 `CheckChassisError`/`CheckResponse` 失败→置 `chassis_error_mask`/`error_code` 并接管。
- 改完协议/控制器必须 `buildtool build -p` 完成 install，新 .so 才会进 `/opt/apollo/neo/lib/modules/canbus_vehicle/<车型>/`（CLAUDE.md 第三节①）。

## 6. 验证命令

```bash
# 已装插件与产物
ls /opt/apollo/neo/src/modules/canbus_vehicle/
ls /opt/apollo/neo/lib/modules/canbus_vehicle/neolix_edu/

# 当前车型是谁（conf gflags）
grep -n "load_vehicle" /apollo/modules/canbus/conf/canbus.conf

# 看 chassis_detail 是否在发（-w 参数本环境是坏的）
cyber_channel -e /apollo/canbus/chassis_detail
cyber_monitor   # 交互看 chassis / chassis_detail 字段

# 编译某车型插件（改完必做）
buildtool build -p modules/canbus_vehicle/neolix_edu
```
