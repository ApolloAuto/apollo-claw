## 0. 一句话作用

### 2.2 轨迹点字段（pnc_point.proto，PnC 公用）

`TrajectoryPoint`（:61-78）= `path_point`(1, :63) + `v`(2, **m/s**, :65) + `a`(3, m/s²，注释缺单位, :67) + `relative_time`(4, **s，相对轨迹起点**, :69) + `da`(5, 纵向 jerk m/s³, :71) + `steer`(6, 前轮转角 rad, :73) + `gaussian_info`(7, :76)。

`PathPoint`（:31-54）= `x`/`y`/`z`(1-3, m, :33-35) + `theta`(4, 航向 rad, :38) + `kappa`(5, 曲率 1/m, :40) + `s`(6, **累计弧长 m**, :42) + `dkappa`(7, dκ/ds, :45) + `ddkappa`(8, :47) + `lane_id`(9, string, :49) + `x_derivative`/`y_derivative`(10-11, :52-53)。

> `relative_time` 会在 component 层被整体平移：`dt = RunOnce 内写的 header 时间 − FillHeader 后的 header 时间`，逐点 `set_relative_time(p.relative_time()+dt)`（planning_component.cc:232-235）。**控制侧按 header.timestamp_sec + relative_time 定位轨迹点，两者必须配对使用。**

### 2.5 空轨迹 / estop 的语义（最容易误判的一段）

- **输入不齐**（localization/chassis/hdmap/planning_command 任一缺失）：`CheckInput` 发一条 **`trajectory_point` 为空**、只有 `location_pose` + `not_ready.reason` + header 的 pb（planning_component.cc:313-317），随后 Proc return false。⇒ `cyber_channel -e /apollo/planning` **有消息不等于规划正常**，要看 `decision.main_decision.not_ready.reason`。
- **vehicle_state 失效 / 建帧失败**：`GenerateStopTrajectory`（:210-230）先 `clear_trajectory_point()`，再用**当前车位置**造一串 `v=0,a=0` 的原地点，时间跨度 `FLAGS_fallback_total_time=3.0` s、步长 `FLAGS_fallback_time_unit=0.1` s（planning_gflags.cc:301-302）⇒ 约 30 个点、`total_path_length=0`。源码自带 TODO 承认「will cause unexpected behavior from controller」（:209）。
- **estop 只在 `FLAGS_publish_estop=true` 时出现**（默认 **false**，planning_gflags.cc:60）⇒ 默认配置下 planning **从不发 estop**，异常一律表达为 not_ready + 原地停车轨迹 + header.status 错误码。想让控制侧收到 estop 必须显式开这个 flag。
- **下游 control 的反应**（引 ../13_control源码/01 §2.3，已核）：`/apollo/planning` 为空或没数据时 control **只告警不退出**（control_component.cc:339-349），靠 `header().sequence_num()` 变化判定新帧才拷贝；真正让 control 不发命令的是 chassis 或 localization 为空（cc:330-336、361-367）。因此「planning 只发 not_ready 空轨迹」的现场表现是：control 仍以 10 ms 周期发命令，但跟踪的是**上一帧旧轨迹**（或零命令），日志里没有明显报错。

## 3. 注册与配置

- **topic 名从哪来**：`/apollo/planning` 的生效值在 planning 自己的 conf（`planning_config.pb.txt` 的 `topic_config.planning_trajectory_topic`，02 篇 §3.2 已核），默认值在 `adapter_gflags.cc:39`；消费侧多数直接用 `FLAGS_planning_trajectory_topic`，prediction/storytelling 用自己 conf 里的同名字段（`prediction_conf.pb.txt:8`、`storytelling_conf.pb.txt:2`）。**改名要三处一起改**（planning conf + 各消费者 conf/flag）。
- **影响输出形态的 gflags**（默认值出自 planning_gflags.cc，运行期被生效 `planning.conf` 覆盖）：`trajectory_time_length`=8.0（:98）、`trajectory_time_min_interval`=0.02（:101-103）、`trajectory_time_max_interval`=0.1（:104-106）、`trajectory_time_high_density_period`=1.0（:107-109）、`publish_estop`=false（:60）、`enable_rss_info`=true（:357）、`enable_planning_smoother`=false（:360）、`fallback_total_time`=3.0 / `fallback_time_unit`=0.1（:301-302）、`planning_loop_rate`=10（:21，只用于 stitching 周期估算）。
- **`enable_record_debug`** 决定 `debug` 字段是否装满参考线/ST 图（:327-328、:533、:640）——关掉能显著减小消息体积。

## 4. 修改与扩展点（二次开发）

**① 给轨迹加字段**（例：加 `optional double my_metric = 27;`）
1. 改 proto：`buildtool install common-msgs`（包名见 `/opt/apollo/neo/share/packages/common-msgs/cyberfile.xml`，`<src_path>//modules/common_msgs</src_path>`）→ 编辑 `/apollo_workspace/modules/common_msgs/planning_msgs/planning.proto`，**tag 号只能新增、不得复用**（`// next id: 24` 注释已过期，现役最大 26，另有 100，取 27 起）。
2. 重编消息包：`buildtool build -p modules/common_msgs`（`bazel build` 不 install，运行时看不见）。
3. 填值：`buildtool install planning` → 在 `on_lane_planning.cc` 的对应阶段 `ptr_trajectory_pb->set_my_metric(...)`（§2.3 选阶段）→ `buildtool build -p modules/planning/planning_component`。
4. **所有依赖 common-msgs 的模块都要重编**（见 §5）；只重编 planning 会出现 planning 写新字段、control 用旧 pb 描述读——protobuf 向后兼容会**静默丢弃**未知字段，不报错。

**② 改轨迹点密度 / 时长**：调生效 `planning.conf`（`/apollo/modules/planning/planning_component/conf/planning.conf`，④ 软链→profile 层，写穿立即生效，重启组件）加 `--trajectory_time_length=`、`--trajectory_time_min_interval=`、`--trajectory_time_max_interval=`、`--trajectory_time_high_density_period=`；默认值与行号见 §3。**不需要重编**。注意 min/max interval 是「发布时的时间采样区间」，真正的点数还受 speed/path 优化器输出长度约束；改完用 `cyber_channel -e /apollo/planning` 数 `trajectory_point` 个数与 `total_path_time` 验证。

**③ 改停车兜底轨迹**：`--fallback_total_time` / `--fallback_time_unit`（同上，conf 改即可）；改逻辑则动 `GenerateStopTrajectory`（on_lane_planning.cc:210-230）。

**④ 加一路新输出 channel**（不动 ADCTrajectory）：在 `PlanningComponent::Init` 里 `xxx_writer_ = node_->CreateWriter<Msg>(topic)`，Proc 内 `FillHeader` 后 `Write`——样板见 planning_component.cc:118-128/:236 与 ../11_cyber框架/04 §4；topic 值优先加进 `planning_config.proto` 的 `TopicConfig`。

## 5. ⚠️ 本环境注意

- **改 common_msgs 的影响面是全仓**：`planning.proto` 被 control / prediction / dreamview{,_plus} / storytelling / monitor / statistics / smart_recorder / tools 直接依赖（§2.6）。包形态下这些模块多为 BINARY 依赖预编译 common-msgs，**改完 proto 必须把消费侧包一并 `buildtool build -p`**，否则运行时新字段被静默丢弃（protobuf 未知字段不报错）。生产环境改公共 proto 前先评估：加字段（optional、新 tag）安全；**改类型/改 tag/删字段会让新旧模块互读出垃圾值**。
- **`FillHeader` 只填 3 个字段且 `sequence_num` 从 0 起**（引 ../11_cyber框架/04 §5，已核 message_util.h:44-52）：`timestamp_sec`/`module_name`/`sequence_num`，其余 6 个 header 字段要么由 `FillPlanningPb` 单独填（lidar/camera/radar timestamp，planning_base.cc:102-107），要么恒空。首帧 `sequence_num=0`（与 header.proto 注释「starting from 1」不符）⇒ **别用 `sequence_num==1` 判首帧**；control 靠 sequence_num 变化判新帧，因此重启 planning 后序号归零可能与 control 缓存的旧序号相同——重启 planning 建议同时重启 control。
- **`FillHeader` 覆盖 `timestamp_sec`**，所以轨迹点 `relative_time` 必须靠 `dt` 平移修正（planning_component.cc:232-235）；自己新增输出若依赖内部时间，要么先取出再修正，要么别调 `FillHeader`。
- **默认不发 estop**（`publish_estop=false`）⇒ 排查「紧急刹停不生效」不要在 `/apollo/planning` 里找 estop；11.0 的刹停链路走 safety_manager → `/apollo/safety/decision`（见 ../13_control源码/01 §2.4）。
- **空轨迹帧也会照发**（:316）⇒ 用「channel 上有消息」判 planning 健康是错的，必须看 `not_ready.reason` 与 `trajectory_point` 个数。
- proto 里 `// next id: 24`（:68）已过期（现役 25/26/100），`LocationPose.vehice_location`（:21）与 `control_interative_topic` 一样是上游拼写错误，**照抄不要纠正**，改了就编不过。
- 搜 `/apollo/...` 用 `grep -R`（`-r` 不跟随符号链接会假空）；conf 落点先 `readlink`（planning 的 planning.conf 指向 `profiles/current`）。
