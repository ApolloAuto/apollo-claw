## 4. 失效 / 无效项清单（本文重点：现象 → 根因 → 判定命令）

### ① `lattice` / `navi` planner：装了但加载不了
- **现象**：把 `planning_config.pb.txt` 的 planner 换成 lattice/navi，日志只 AWARN `library[...] invalid`，`CreateInstance<Planner>` 返回 nullptr。
- **根因（本轮逐层核实）**：索引文件名按真实 .so 路径生成
  （`cyber_plugin_index/modules__planning__planners__lattice__liblattice_planner.so`，内容
  `share/modules/planning/planners/lattice/plugins.xml`），而该 xml 里 `<library path=...>` 写成
  `modules/planning/planners/public_road/liblattice_planner.so`（navi 同样错）——`public_road/` 下**只有**
  `libpublic_road_planner.so` 与 `proto`。上游 bug，本机原样安装。加载失败点见 03 篇（`plugin_manager.cc:51、75-80`）。
- **判定**：`cat /opt/apollo/neo/share/modules/planning/planners/lattice/plugins.xml`；
  `ls /opt/apollo/neo/lib/modules/planning/planners/public_road/`（无 lattice/navi so 即确诊）。
- **修法**：改 plugins.xml 的 `path` 为各自目录 → `buildtool build -p modules/planning/planners`。

### ② navi 系三个文件：改了永远无效
`conf/navi_planner_config.pb.txt`、`conf/planning_navi.conf`（→share）、`dag/planning_navi.dag`（→share）都存在，
但：`launch/` 下**没有** navi launch；navi 分支要 `FLAGS_use_navigation_mode=true` 才实例化 `NaviPlanning`
（默认 false，02 篇 §1）；且 NaviPlanner 插件本身命中 ①。三条叠加 = 死配置。
**判定**：`ls /apollo/modules/planning/planning_component/launch/`（只有 `planning.launch`）。

### ③ 7 个孤儿实例 conf：静默走 default，参数「改了没效果」
根因机制：`ConfigUtil::LoadMergedConfig` 读不到实例 conf 只 AWARN 后 `return true`（引 09 篇 `config_util.h:86-89`）；
文件名规则是 pipeline 里 **`name` 别名的 tolower**（`config_util.cc:26-30`），与类名无关。
本轮在 ④ 视口逐 scenario 对齐 pipeline 别名，实测 **7 个文件永不被读**：

| 孤儿 conf（相对 `/apollo/modules/planning/scenarios/`） | 落点 | 该 stage 的真实别名 |
|---|---|---|
| `large_curvature/conf/large_curvature/open_space_rt_optimizer.pb.txt` | profile | 无此别名（该 stage 6 个别名已核） |
| `large_curvature/conf/large_curvature/open_space_trajectory_optimizer.pb.txt` | profile | `OPEN_SPACE_TRAJECTORY_OPTIMIZER_PARK` |
| `valet_parking_park/conf/valet_parking_parking_park/open_space_trajectory_optimizer.pb.txt` | profile | 同上 |
| `valet_parking_park/conf/valet_parking_retry_park/open_space_trajectory_optimizer.pb.txt` | profile | 同上 |

`diff` 出厂/生效版 `valet_parking_park/conf/pipeline.pb.txt` 实测 `:75-76`、`:104-105` 把

**判定命令**：见 §8「孤儿实例 conf 全量扫描」。

### ④ 参考线独立线程被关：不是「50ms 后台刷新」
`planning.conf:57 --enable_reference_line_provider_thread=false`（本轮 grep 核对行号）→ 参考线在
`GetReferenceLines` 内**同步**计算（引 08 篇 / 漂移表 #23：`reference_line_provider.cc:326-334`）。
后果：一帧规划耗时含平滑耗时，「planning 周期变长/掉帧」先查这条；同档 `:15` 还关了参考线 stitching。
按线程模型写的排查步骤（查生成线程日志、查线程 CPU）在本机全部不适用。

### ⑤ planning 框架基类不可读、两个包没 install
`planning_interface_base` 是**纯 binary 包**：`Scenario`/`Stage`/`Task`/`TrafficRule`/`Planner` 只有头文件（include 树）
+ `.so`，`.cc` 在 src / include / 工作区三处都不存在（漂移表 #22；05/06 篇 §5 同结论）。
① 层实测 8 个包（`park_data_center planners planning_component planning_open_space pnc_map scenarios tasks traffic_rules`）
+ 一个 `BUILD`，**缺 `planning_base`、`planning_interface_base`**。
后果：`Task::Init`、`Stage::ExecuteTaskOnReferenceLine`、`TrafficDecider::Execute` 的函数体**本机看不到**，
相关断言只能靠头文件签名 + `nm -DC` 推断；想改 gflags（在 `planning_base`）必须先 `buildtool install planning`。
**判定**：`ls /apollo_workspace/modules/planning/`；`ls /opt/apollo/neo/src/modules/planning/planning_interface_base/`。

### ⑥ 其它本轮发现的现状项
- **`libDO_NOT_IMPORT_planning_component.so` 与 `libplanning_component.so` 并存**于同一 lib 目录。dag 里
  `module_library` 指的是后者（02 篇 §3.1），**不要**把前者写进 dag 或 BUILD 依赖。
- **`SQUARE` 场景整条链是死的**：conf 里被注释（未注册）+ 它唯一的实例 conf 还是孤儿 → 改 `square/` 下任何 conf 都无效，
  要用先在 `public_road_planner_config.pb.txt` 里解注释（注意排在 `LANE_FOLLOW` 之前）。
- **出厂 share 档 ≠ 现状**：`grep` 到 share 里的 12 scenario / 10 rule / 限速 20 都不是本机生效值；
  `00_readme.md:70` 对本文的旧描述（「已注册 12 scenario/9 rule」）同样已过期，以 §3 为准。

## 6. 「planning 起来了但没轨迹」排障树

先看 `/apollo/planning` 有没有消息、内容是不是空轨迹：`cyber_channel -e /apollo/planning`。
**输入不齐时 planning 仍会发一帧空轨迹**并在 `decision.not_ready.reason` 写原因（引 02 篇：
`planning_component.cc:190-193` → `284-320`，写点 `:316`）——先读这个字段，能直接跳分支。

| 分支 | 典型现象 | 判定命令 | 去哪篇 |
|---|---|---|---|
| A 输入缺失 | `not_ready.reason` = `localization not ready` / `chassis not ready`；或**完全没有** `/apollo/planning` 消息（prediction 没来，planning 根本不触发） | `cyber_channel -l`；`cyber_channel -e /apollo/prediction`；`ls -l /apollo/modules/prediction/dag/prediction.dag` | [../14_数据与消息/01](../14_数据与消息/01_PnC链路channel全景.md) §2.3、[02](02_planning_component主循环.md) §2.2 |
| B 地图缺失 | `not_ready.reason` = `map not ready`；或有轨迹但参考线为空 | §5 检查 1-2（末行 `--map_dir` 指向的目录是否存在、有无 `base_map.bin`） | [08](08_pnc_map与参考线.md)、本文 §5 |
| C 场景没切 | 一直停在 `LANE_FOLLOW`，新加的场景从不进入 | `cat /apollo/modules/planning/planning_component/conf/public_road_planner_config.pb.txt`：目标场景是否在表里、是否排在 `LANE_FOLLOW` **之前**（first-match；`LaneFollowScenario::IsTransferable` 在 lane_follow 类命令下无条件 true —— 04 篇 `lane_follow_scenario.cc:29-41`）。卡在某 stage 不动 → 查 `next_stage_` 别名（05 篇：stage 列表只有第一条是入口） | [04](04_scenario框架.md)、[05](05_stage框架.md) |
| D conf 没生效 | 参数改了行为不变，日志只有 `can not load user defined config file` 之类 AWARN | `readlink -f <改的文件>` 确认改的是生效落点（§2）；用 §8 扫描确认文件名与 pipeline 别名一致（§4③）；改 ① 层源码则确认已 `buildtool build -p` | [09](09_conf与gflags体系.md) §5、本文 §4③ |
| E 插件没装/加载失败 | 进程直接 `ACHECK` 退出（scenario 注册项写错 —— 03/04 篇 `scenario_manager.cc:43-44`）；或 AWARN `library invalid` 后功能静默缺失（planner/task 加载失败，§4①） | `ls /opt/apollo/neo/share/cyber_plugin_index/ \| grep <关键词>`；`cat <包>/plugins.xml` 核 `path` 与 `base_class`（必须写最顶层基类）；改插件后必须 `buildtool build -p` 才 install | [03](03_planners_public_road.md)、[06](06_task框架与task大族.md)、[07](07_traffic_rule框架.md) |

**两种失败模式别互相套用**：scenario/planner 的**注册清单**写错 = `ACHECK` 崩；stage/task 的**实例 conf** 写错 = AWARN 静默降级。
另：某条 traffic_rule 返回非 OK 会把该参考线判为不可驾驶（07 篇 `on_lane_planning.cc:365-369`），
表现是「有轨迹但一直停车」而不是「没轨迹」。
